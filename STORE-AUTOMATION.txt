ONE-TIME API CONNECTION

The Microsoft Store submission API authenticates an automation application,
not your interactive Microsoft account password.

1. Partner Center -> Account settings -> Tenants: associate an existing
   Microsoft Entra ID directory, or create/link one as supported by your account.
   Setting up that association requires the appropriate tenant administrator.
2. Account settings -> Users: add/create an Entra application for Orbs publishing
   and assign the Manager role required by the Store submission API.
3. Open that application and record its Tenant ID and Client ID. Create a client
   key/secret, storing its VALUE and expiry securely. Do not put it in Git, a
   workflow YAML file, a command-line argument, or this chat.
4. Set the following environment variables in the process that runs the script,
   or inject them from your CI system's encrypted secret store:
     PARTNER_CENTER_TENANT_ID
     PARTNER_CENTER_CLIENT_ID
     PARTNER_CENTER_CLIENT_SECRET
5. Copy the Flight ID from the flight's Partner Center URL. This is a GUID;
   it is different from the Store product ID and the tester group ID.

Official authentication/prerequisite documentation:
https://learn.microsoft.com/en-us/windows/uwp/monetize/create-and-manage-submissions-using-windows-store-services

LOCAL COMMANDS (POWERSHELL 7.2 OR NEWER)

This PC also supports Windows DPAPI-encrypted publisher credentials at
%LOCALAPPDATA%\DubaTech\StorePublishing\credentials.clixml. The file contains
TenantId and a PSCredential (client ID as username, client secret as password).
It can only be decrypted by the same Windows account on this computer. When
all three PARTNER_CENTER variables are absent, the publisher reads this file.
If any environment variable is supplied, all three are required. The encrypted
credential file and the original desktop key file must never be committed.
Verified API access with this configuration on 2026-11-06.

Use the Store .appxupload already built and tested. The examples below use $pkg
for its absolute path and $flight for the flight ID. No credentials are needed
for Plan, which inspects the actual package identity/version and reports SHA256.

  .\build\Publish-StorePackage.ps1 -Action Plan -PackagePath $pkg -FlightId $flight

Create, upload and commit a flight update for certification:

  .\build\Publish-StorePackage.ps1 -Action Submit -PackagePath $pkg -FlightId $flight

The result includes SubmissionId, package hash, and requested publishing mode.
Successful commit is not certification success or publication. Check status:

  .\build\Publish-StorePackage.ps1 -Action Status -FlightId $flight -SubmissionId <id>

Use the exact same artifact for production after testing. By default this submits
for certification and holds publication for your release action in Partner Center:

  .\build\Publish-StorePackage.ps1 -Action Submit -Target Production -PackagePath $pkg

To publish to normal users automatically once certification succeeds, explicitly
request Immediate when creating the production submission:

  .\build\Publish-StorePackage.ps1 -Action Submit -Target Production -PackagePath $pkg -PublishMode Immediate

Check the production submission:

  .\build\Publish-StorePackage.ps1 -Action Status -Target Production -SubmissionId <id>

CI INTEGRATION

These are normal noninteractive commands suitable for a GitHub Actions release
job. Build once with Build-StorePackage.ps1 -Channel Store, retain the artifact,
submit it to the personal flight, then reuse that artifact for production. Keep
the production release as a separate manually dispatched job/environment. Inject
the three credentials above as environment variables from encrypted secrets.
The helper does not require Azure CLI, an Azure subscription for blob storage,
or a local signing private key; Partner Center supplies its upload destination.

Do not mix dashboard edits with API edits on the same in-progress submission.
Microsoft documents that this can prevent further API changes/commit. Status
inspection in Partner Center is fine. If a draft already exists, this helper
stops and reports its ID; it never deletes or overwrites a pending submission.
If a request fails after creating a submission, its ID is reported for recovery.

The helper appends the new package and retains older architectures, listings,
prices, and existing rollout options. It does not create tester groups or flights;
those are configured once above. Microsoft also exposes flight creation in the
API if that is needed later.

When Microsoft creates an initial flight draft automatically, its ID can be
resumed explicitly with -SubmissionId <id> on a flight Submit command, provided
it is still the current PendingCommit draft. Only resume drafts created by the
API; dashboard-edited drafts are not safe to modify through the API. Production
drafts are never resumed by this helper.
